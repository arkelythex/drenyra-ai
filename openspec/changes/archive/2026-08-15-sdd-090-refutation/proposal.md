# Proposal — SDD-090 Refutation Dual-Review and Findings Resolution

## Intent

Complete the first missing Guardian Angel verification-lens slice with pure,
read-only libraries for finding-scoped refutation dual-review and findings
resolution. The change makes adversarial findings challengeable and closable
without granting Guardian records any approval authority.

This proposal selects exploration Option A:

- add `guardian/refutation.ts` and `guardian/resolution.ts`;
- export both through `guardian/index.ts`;
- add focused unit tests; and
- leave `runGuardianReview` and the CLI behaviorally unchanged.

The honest estimate is approximately 1,100–1,500 authored lines. Runtime guards,
immutable outputs, typed denials, lifecycle coverage, and adversarial tests make
this larger than the normal review budget.

## Roadmap and architecture context

SDD-090 belongs to Wave 2 of the approved 16-program Peru v1 roadmap. It advances
the Guardian Angel verification capability that depends on SDD-040 frozen
candidates and feeds future SDD-100 Command Center presentation.

The slice remains within Drenyra-AI's advisory orchestration role:

- Drenyra Core retains deterministic accounting authority.
- Findings, refutation outcomes, and resolutions are advisory evidence.
- None participates in an approval quorum or holds authority state.
- The audit ledger remains audit-only; no accounting journal entry is created.
- These records are evidence, not memory or a source of durable authority.
- Tenant, ingest, policy, evidence, journal, and SUNAT-facing integrations remain
  deferred unless a later SDD explicitly scopes them.

The approved layer model is `contracts -> library modules -> agents -> cmd`.
This slice adds library modules and tests only, with no reverse imports. It closes
a verification-lens gap without promoting SDD-090 or a capability-matrix row.

## Current state and gap

`guardian/guardian.ts` implements the read-only single-review core:

- `runGuardianReview(candidate, options): GuardianReport` emits findings;
- reports bind to `candidateHash` and have `verdict: "none"`;
- findings contain `id`, severity, category, and description;
- candidates are not mutated; and
- the existing CLI exposes findings-only review.

The exploration verified zero TypeScript symbols for refutation, refuters,
dual-review, or findings resolution. Guardian can report a suspected problem,
but the library cannot challenge it, obtain two independent judgments, identify
disagreement, close the finding, or reject stale resolution after identity change.

`GuardianFinding.id` is generated by a module-level sequence, not content. It is
therefore an opaque, process-scoped handle, not a portable finding identity.
Ad hoc downstream solutions would risk both identity errors and erosion of the
boundary between advisory review and deterministic authority.

## Proposed change

### Finding-scoped refutation

Add `guardian/refutation.ts` as a pure library. A `RefutationChallenge` targets a
`GuardianFinding`, uses its `findingId` as an opaque handle, and retains enough
finding data to anchor the challenge to the same review output.

All findings are challengeable. The model has no `finding.kind`, and Guardian is
adversarial by design. Restricting challenges to an undefined “inferential” type
would invent a classification with no current producer or consumer.

The closed `RefutationVerdict` vocabulary is:

- `uphold`: the challenged finding stands;
- `refute`: the finding is rejected; and
- `downgrade`: it remains relevant, but severity is overstated.

A dual review contains exactly two independent reviewer judgments. Reviewer IDs
must differ from each other and from the challenger. The result is `consistent`
if and only if both valid reviews have the identical verdict. Different verdicts
or invalid independence produce a fail-closed, escalation-needed outcome.

Escalation is advisory. This slice does not choose a winner, invoke a third
reviewer, approve, reject, or block a candidate.

### Findings resolution

Add `guardian/resolution.ts` as a pure lifecycle library. Each known finding starts
`open` and may transition once to `resolved` or `dismissed`.

A `ResolutionRecord` binds the finding, actor, disposition, reason, optional
evidence reference, caller-supplied timestamp, and reviewed candidate identity.
The library reads no clock. It supports no reopen, revocation, or carry-over.

When candidate identity changes, prior findings and resolutions are stale. The
library must deny the transition with `candidate-changed` and require a fresh
Guardian review.

The closed typed denial vocabulary will cover at least:

- `unknown-finding`;
- `already-resolved` and `already-dismissed`;
- `empty-reason`, `missing-actor`, and `missing-timestamp`;
- `malformed-record`; and
- `candidate-changed`.

Names may be normalized in specification/design, but semantics must not weaken.
Invalid untrusted input fails closed without throwing or mutating caller objects.

### Advisory-only and immutable invariants

Both modules follow the established pure-library precedent:

- no candidate mutation, execution, approval, rejection, or quorum signal;
- no authority state and no `CandidateReviewVerdict` reuse;
- immutable records, readonly collections, and frozen created outputs;
- deterministic output for identical inputs;
- caller-supplied timestamps, never clock reads;
- runtime shape validation for untrusted input; and
- discriminated success/denial results for expected domain failures.

A refutation verdict concerns a finding. A resolution disposition records a
finding lifecycle transition. Neither is a candidate verdict.

## Affected areas

```text
guardian/
  guardian.ts                    unchanged live findings-only reviewer
  refutation.ts                  new pure challenge/dual-review library
  resolution.ts                  new pure finding lifecycle library
  index.ts                       add public exports
  __tests__/refutation.test.ts   new
  __tests__/resolution.test.ts   new
```

The new modules may import Guardian types from the same library layer. Contracts,
agents, flows, gates, commands, audit ledgers, journals, and Command Center code
remain unchanged.

## Requirements preview

The specification will refine these drafts using RFC 2119 keywords and
Given/When/Then scenarios.

### REQ-GU-001 — Finding binding

A challenge MUST bind to a finding from the same review and preserve its ID as an
opaque handle. The API SHOULD anchor more than a free-standing raw ID.

### REQ-GU-002 — Challenge coverage

Every Guardian finding MUST be challengeable regardless of severity or category.
The slice MUST NOT add a `finding.kind` distinction.

### REQ-GU-003 — Closed verdict set

A review MUST use exactly `uphold`, `refute`, or `downgrade`. Unknown values MUST
fail closed.

### REQ-GU-004 — Dual-review independence

An evaluation MUST contain exactly two distinct reviewers, both independent from
the challenger. Invalid independence MUST NOT produce consistency.

### REQ-GU-005 — Consistency

A dual review MUST be `consistent` iff both valid verdicts are identical. Different
verdicts MUST be `inconsistent`.

### REQ-GU-006 — Escalation

Invalid or inconsistent review MUST emit an escalation-needed advisory result and
MUST NOT approve, reject, or block a candidate.

### REQ-GU-007 — Resolution lifecycle

A known finding MUST begin `open` and MAY transition once to `resolved` or
`dismissed`. A terminal finding MUST NOT transition again in this slice.

### REQ-GU-008 — Advisory-only boundary

Outputs MUST NOT alter candidate verdicts, participate in quorum, execute a
candidate, hold authority, or mutate candidate data.

### REQ-GU-009 — Fresh review

Identity mismatch MUST return `candidate-changed`. Findings, challenges, and
resolutions MUST NOT carry over to a changed candidate.

### REQ-GU-010 — Immutable deterministic records

Created records MUST be immutable and collections readonly. Equivalent inputs
MUST produce equivalent outputs.

### REQ-GU-011 — Typed denials

Invalid domain input and lifecycle transitions MUST return closed typed denials.
Expected invalid input MUST NOT require exception handling.

### REQ-GU-012 — No clock

The libraries MUST NOT read the system clock. Timestamps MUST be caller-supplied
and validated according to the final contract.

### REQ-GU-013 — Barrel exports

Supported symbols MUST be exported from `guardian/index.ts` using ESM `.js`
conventions.

### REQ-GU-014 — Unit evidence

English unit tests MUST cover consistency, independence, lifecycle, every denial
class, identity change, immutability, determinism, and non-mutation/authority.

## First-slice scope

In scope are challenge validation, the closed verdict set, two-reviewer
independence and consistency, inconsistent escalation, open-to-resolved/dismissed
transitions, immutable records, typed denials, barrel exports, and unit tests.

## Non-goals

No wiring into `runGuardianReview`, Guardian report/finding shapes, CLI, Command
Center, contracts, agents, flows, gates, ledgers, journals, policy, ingest, tenant,
evidence, or SUNAT-facing integrations. The slice adds no authority/quorum signal,
third reviewer, automated escalation, resolution reopen/carry-over, content-derived
finding IDs, capability promotion, or harness-side refuter-agent model. It does not
modify or reuse `CandidateReviewVerdict`.

## Tradeoffs

**Option A (selected)** proves pure contracts with the lowest live regression risk,
but has no user-facing workflow. **Option B (deferred)** adds Guardian wiring but
changes report shapes and risks making advisory state look approval-like. **Option C
(deferred)** adds CLI access but freezes command and persistence semantics before the
domain contract is proven. Option A secures governance before integration and follows
the repository's pure-library-first precedent.

## Risks and mitigations

**Finding ID stability — high.** IDs are process-local. Bind to findings from the same
report, carry candidate identity, treat IDs as opaque, and deny mismatch.

**Scope creep — medium.** Keep the Option A file/behavior boundary; wiring is another
slice.

**Advisory-boundary drift — medium.** Separate finding and candidate types, omit
authority fields, and test that outputs cannot approve, block, execute, or mutate.

**Forecast undercount — medium.** The 300/400-line budgets are below the 1,100–1,500
estimate. Record a size exception or chain the work; never reduce invariant coverage.

## Rollback

Revert the two modules, tests, and barrel exports. There is no live wiring or
persisted authority state, so existing Guardian and CLI behavior is unchanged.
Experimental records are advisory and require no authority rollback. Candidate
identity change independently requires fresh review.

## Success criteria and test hints

Success requires identical independent verdicts to be `consistent`, differences to
escalate as `inconsistent`, and invalid independence to fail closed. Only the three
closed verdicts are accepted; all findings are challengeable; lifecycle transitions
are one-way with typed denials; identity change returns `candidate-changed`; inputs
remain unchanged; outputs are immutable/deterministic and non-authoritative; no clock
is read; barrel exports work; and existing Guardian/CLI behavior remains green.

Tests explicitly cover the SDD-090 metrics: consistency for inferential-style findings,
read-only enforcement, and re-review whenever candidate identity changes.

## Delivery shape

Preferred delivery is one PR for both mutually dependent modules, exports, and
tests, with a documented size exception. The 1,100–1,500 authored-line estimate
exceeds both review budgets, but keeping the denial and invariant matrix together
avoids publishing an incomplete lifecycle contract.

If reviewability degrades, use a chained split without reducing coverage:

1. refutation contract and tests;
2. resolution lifecycle and tests; then
3. final barrel/invariant integration only if necessary.

The fallback must preserve Option A and must not absorb wiring or CLI work.

## Open questions

1. Must each operation receive the whole `GuardianFinding`, or a frozen anchor with
   ID, severity, category, and description?
2. Is `candidateHash` sufficient proof of same-review freshness, or should the API
   use a dedicated immutable review identity record?
3. Should malformed/missing dual input be a typed denial distinct from valid-but-
   disagreeing `inconsistent`, while both remain fail-closed and non-authoritative?
4. Must `downgrade` include and validate a strictly lower target severity?
5. Should timestamps be ISO-8601 validated or treated as non-empty caller-owned
   evidence strings? The library will read no clock either way.

These refine the contract without reopening Option A or the advisory-only boundary.
